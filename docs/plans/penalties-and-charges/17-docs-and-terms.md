# 17: Доки, термины и записи решений

**Суть.** KB и код обязаны называть одно и то же одними словами, а решения
грилла — жить в `docs/decisions/`, чтобы свежий контекст не пересматривал их
заново. Тикет закрывает документационный слой плана.

**Сегодня.** Терминов «часть долга», «начисление», «просроченная сумма»,
«неустойка», «издержки», «правило распределения платежа», «шкала неустойки» в
`CONTEXT.md` нет; `finance_core/README.md` не знает о частях, начислениях и
правилах зоны.

**Будет.** Термины в `CONTEXT.md` с определениями из решений грилла и пометками
«не говорить» (неустойка — не «пеня» и не «штраф», начисление — не «комиссия»,
часть — не «статья»). `finance_core/README.md` описывает устройство частей,
начислений от события, просроченной суммы, правил зоны и what-if ровно по коду.
Записи решений в `docs/decisions/`: части долга и начисления; неустойка и
просроченная сумма; начислено и уплачено; правила зоны и их формы — со
ссылками на раунды грилла.

**Решения грилла плана.** Исполняет R4-Q24 (новые термины глоссария),
R4-Q22 (приёмка: линт KB, синхронизация документации с кодом), R9-Q39 (критерий
записей решений); документирует
решения раундов 1–10 (Q1–Q39) и правки 1–3. Новых решений не принимает.

**Blocked by:** 07, 09, 10, 11, 12, 13, 14, 15, 16 (документация описывает
финальное состояние всех способностей).

## Грилл тикета

План решил **что** строить (R4-Q22, R4-Q24, Q28–Q39 — приняты), тикет решает
**как**: какие термины заводить, какие записи решений писать, чем заканчивать
синхронизацию. Фронтюр раунда 1: термины, записи решений, README и экспорт —
три независимые ветви документационного слоя.

### Раунд 1 — термины, записи решений, README и экспорт

❓ **17-Т1** — **Термины в `CONTEXT.md`**: R4-Q24 назвал семь терминов; нужно
решить их форму и пометки «не говорить».

➡️ Рекомендация (принята): завести термины с определениями из решений грилла и
пометками «не говорить»: **часть долга** (тело, проценты, неустойка, издержки;
не «статья» и не «категория»), **начисление** (рост долга от события: запись или
правило; не «комиссия»), **просроченная сумма** (остаток потока после срока,
ограниченный остатком долга; не «аррерис» и не «недоплата» — недоплата это
метрика `short`), **неустойка** (капает по шкале от срока; не «пеня» и не
«штраф» — штраф это основание начисления), **издержки** (разовые суммы от
событий: пошлина, решение суда; не «расходы»), **правило распределения платежа**
(очерёдность частей; не «приоритет»), **шкала неустойки** (ступени от срока; не
«тариф»). Порядок — по возрастанию важности: часть долга → начисление →
просроченная сумма → неустойка → издержки → правила. Восьмой термин —
**переплата** (R6-Q33, расширен 16-Т3: тело может уйти в минус): платёж сверх
всех частей — избыток несёт тело, канон равен сумме частей; это термин, а не
тактика, и не «досрочка».

*Отклонено:*
- **один термин «начисленное» на всё** — проценты, неустойка и штрафы имеют
  разную механику и разные вопросы владельца;
- **свободные синонимы** (пеня/неустойка/штраф как равные) — ёлка из слов
  (R4-Q24 отверг);
- **термины только в README движка** — глоссарий живёт в `CONTEXT.md`
  (правило `engine-wording`).

❓ **17-Т2** — **Записи решений в `docs/decisions/`**: какие решения увековечить
и как их связать (правило KB: документ без ссылок — сирота, ошибка).

➡️ Рекомендация (принята): **критерий — Q39: запись получает решение, которое
меняет долговременное правило движка и переживёт этот план** (будущий цикл
находит его вне контекста плана); имена, формы, состав тестов и порядок работ
остаются плановыми. По критерию — четыре записи, по числу устойчивых решений:

1. **«Части долга и начисления от события»** — Q1, Q2, Q5, Q6, Q10, Q17, Q18,
   Q19, Q21, Q23, Q27, Q28, Q34, Q38, правка 2, правка 3: канон = сумма частей
   (условно — Q34), запись-начисление с уидом события, цель копилки от тел,
   дельта передачи в тело, закрытость по телу, мост «платёж → вхождение ↔
   части», `balance` := Σ `parts`;
2. **«Неустойка и просроченная сумма»** — Q4, Q7, Q13, Q15, Q20, Q26, Q31, Q36,
   правка 1: база (исходная просроченная сумма — обрезанный поток 05), шкала,
   потолок («без потолка» — явная форма), без компаунда на неустойку, what-if
   теми же функциями, разведение метрики `short` и просрочки;
3. **«Начислено и уплачено»** — Q8, Q14, Q16, Q30, Q33, Q37: один факт — один
   носитель, пара денег, замороженная нагрузка, досрочка — тот же платёж,
   несвязанное движение гасит просрочки, переплата на теле, `Movement.event`;
4. **«Правила зоны и их формы»** — Q3, Q9, Q11, Q12, Q25, Q29, Q35: формы,
   версии эпох, ключ случая (uid, дата), правило из данных, одно правило
   распределения.

Каждая запись — `node_type: decision`, `status: active`, `updated` — дата
правки, `links.depends_on`/`relates_to` на `docs/decisions/derived-balances.md`,
`unknown-is-not-zero.md` и план; `docs/decisions/README.md` пополняется
строками. Каждая запись цитирует номера вопросов грилла — чтобы свежий контекст
не пересматривал. **Плановые решения** (критерий Q39 — не правила движка):
Q22 (приёмка — порядок проверки), Q24 (термины — живут в `CONTEXT.md`), Q32
(суперсед-пометки — способ читать грилл), Q39 (сам критерий — живёт в этом
плане и в приёмке ниже). Покрытие проверяемо грепом: каждый номер Q1–Q39 и
правок 1–3 либо цитируется в одной из четырёх записей, либо помечен плановым
здесь.

*Отклонено:*
- **одна запись на всё** — четыре разных решения с разными последствиями;
- **записи без ссылок** — сироты, линт KB упадёт;
- **продублировать весь грилл в решениях** — грилл уже записан в плане, решения
  цитируют его номера.

❓ **17-Т3** — **README движка и полнота экспорта**: `finance_core/README.md`
должен описывать ровно то, что делает код; `__init__.py` — полный список новых
публичных имён (они названы в Scope и в приёмке).

➡️ Рекомендация (принята): обновить README движка разделами по новой механике
(части и раскладка, начисления и триггеры, просочка и неустойка в книге и в
прокате, распределение платежа, what-if) — ровно по коду, без обещаний;
`finance_core/__init__.py` — экспорт полного списка имён (`Charge`, `PARTS`,
`deal_parts`, `PartPayment`, `allocate_payment`, `rule_at`, формы правил,
`overdue_amounts`, `overdue_amount`, `accrued_penalty`, `trigger_charges`,
`TriggeredCharge`, `deal_growth`, `DebtGrowth`);
докстринги функций и полей — по терминам 17-Т1.

*Отклонено:*
- **README с пересказом плана** — README описывает код, план живёт в плане;
- **экспорт «на вырост»** (лишние имена) — список полон и осознан, «что
  попало» — нет (Scope);
- **переименование старых имён ради красоты** — ломает потребителя без выигрыша.

Фронтюр после раунда 1: порядок работ и состав финальной проверки зависят от
решений выше — раунд 2.

### Раунд 2 — порядок работ и финальная проверка

❓ **17-Т4** — **Порядок и состав финальной проверки**: тикет закрывает цикл
планов; нужно решить порядок правок и чем проверять, что ничего не упущено.

➡️ Рекомендация (принята): порядок правок — **термины → записи решений → README
→ экспорт** (глоссарий раньше кода: докстринги ссылаются на термины). Финальная
проверка:

1. **линт KB канонической копией** — чисто, `index` перестроен;
2. **`python3 -m pytest tests/`** — синтетика движка зелёная (по `Constraints`:
   после каждой правки движка; здесь движок уже собран, прогон — сверка);
3. **сверка списков**: `__init__.py` содержит все имена из Scope; README
   описывает всё из Done; термины в `CONTEXT.md` употреблены в README и
   докстрингах одинаково;
4. **сценарные тесты зоны** — оператор (движок их не видит; R4-Q22).

*Отклонено:*
- **линт вместо прогона тестов** — линт проверяет KB, не код;
- **прогон сценариев зоны движком** — зона приватна;
- **автогенерация README из кода** — README пишется человеком, автогенерация
  дала бы пересказ сигнатур без смысла.

Фронтюр после раунда 2 пуст: термины, записи, README, экспорт, порядок и
проверка определены — документационный слой закрывает цикл грилла тикетов.
