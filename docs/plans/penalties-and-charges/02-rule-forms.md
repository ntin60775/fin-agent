# 02: Формы правил зоны, их версии и валидация

**Суть.** Ставки, пороги, потолки и порядки распределения приходят снаружи и в
движок не вшиты — но движок обязан их понимать и проверять. Тикет заводит
**закрытый набор форм правил зоны** и валидацию книги: шкала неустойки (ступени
«от N дней просрочки — дневная ставка»), потолок («без потолка», сумма или доля
просроченной суммы), порядок распределения платежа (перестановка частей),
условие триггера (закрытый набор); правила версионируются по дате действия.

**Сегодня.** Правила — только ставки сделки и правило графика (`ScheduleRule`,
закрытый набор форм, `finance_core/settlements.py:161`); шкал, потолков,
порядков распределения и триггеров в модели нет; версий правил нет.

**Будет.** Формы правил — данные модели (закрытый набор, как `ScheduleRule`):
расширение — новая форма кодом движка, а не произвольной структурой зоны. У
каждой версии правила есть дата действия; правило без даты действует на весь
период; движок выбирает правило по дате отрезка или платежа. Валидация падает
текстами по существу: ступени возрастают и не отрицательны, потолок не
отрицателен, порядок — перестановка без повторов и со всеми частями. Правила
нет — `None` («не задано»), а не ноль; «без потолка» — явная форма, а не
отсутствие данных.

**Решения грилла плана.** Исполняет R1-Q3 (правила приходят снаружи, считает
движок), R3-Q12 (закрытый набор форм, тексты валидации, неизвестное —
`None`/пробел), R4-Q25 (версии правил по дате действия), правку 1 («без
потолка» — явная форма правила, не `None`). Новых решений не принимает.

**Blocked by:** 01 (объявленный набор частей — для порядка распределения).

## Приёмка

- [ ] Синтетика: корректные формы правил проходят валидацию; каждое нарушение
  (убывающие ступени, отрицательная ставка или потолок, порядок с повторами или
  без части) падает с текстом, называющим правило и что исправить —
  `tests/test_settlements.py`.
- [ ] Синтетика: правило с датой действия обслуживает только свои даты — прошлое
  считается правилом своей эпохи; правило без даты действует весь период —
  `tests/test_settlements.py`.
- [ ] Синтетика: отсутствие правила не подставляется нулём — признак «правило не
  задано» (`None`) отличим от «без потолка» — `tests/test_settlements.py`.
- [ ] Факт: умолчаний правил в коде движка нет (`finance_core/README.md`,
  инварианты).

## Грилл тикета

План решил **что** строить (R1-Q3, R3-Q12, R4-Q25, правка 1 — приняты), тикет
решает **как**: формы данных правил, их версии, валидация с текстами. Фронтюр
раунда 1: где живут правила и как датируются; форма каждой из четырёх форм
правила; тексты ошибок. Исполнение правил (срабатывание, начисление, расчёт) —
ти́кеты 06 и 07: тикет только задаёт форму и проверяет её.

### Раунд 1 — формы правил, версии и тексты валидации

❓ **02-Т1** — **Где живут правила и как версионируются**: правило — данные
зоны на сделку (R1-Q3); версии — с датой действия, как версии тела (R4-Q25);
«правило без даты действует на весь период» (R4-Q25).

➡️ Рекомендация (принята): правила — поля `Deal`
(`finance_core/settlements.py:192`): `penalties: tuple[PenaltyRule, ...]`,
`allocations: tuple[AllocationRule, ...]`, `triggers: tuple[TriggerRule, ...]`.
Каждая версия несёт `effective: date | None`. Выбор по дате — функция
**`rule_at(rules, on)`** в `settlements.py`: действующей считается последняя
версия с `effective <= on`; версия без `effective` действует с начала периода;
версия без даты допустима, только если версий у правила ровно одна (иначе
неоднозначность — валидация). Валидация: даты действий в кортеже строго
возрастают.

*Отклонено:*
- **отдельная сущность «версия правил» (как `Assignment`)** — версии тела
  создаёт событие передачи, а правила зоны правятся её данными: датированное
  правило уже несёт дату, второй сущности не нужно;
- **правила вне сделки** (реестр правил по контрагентам) — правило кредитора
  действует на конкретную сделку (R2-Q9);
- **`dict[date, Rule]`** — словари не носители модели: модель держит dataclass
  и кортежи.

❓ **02-Т2** — **Шкала неустойки: форма ступеней**: R3-Q12 — ступени «от N дней
просрочки — дневная ставка»; Q13 — ставка действующей ступени на день, первый
день просрочки — день после срока.

➡️ Рекомендация (принята): **`PenaltyRule`** — правило неустойки целиком (шкала
и потолок — один носитель: у правила неустойки одно содержимое): поля `steps:
tuple[PenaltyStep, ...]`, `cap: PenaltyCap`, `effective: date | None = None`.
**`PenaltyStep(days: int, rate: Decimal)`** — «от `days` дней просрочки —
дневная ставка `rate`». Ступень действует **включительно** («от N дней» — с N
включительно); действующая на день — с наибольшим `days`, не превышающим
возраст просрочки; возраст дня = число дней со дня после срока (день после
срока — возраст 1). Валидация: `days >= 0`, пороги строго возрастают, `rate >=
0`, ступеней хотя бы одна.

*Отклонено:*
- **параллельные кортежи `days` и `rates`** — расхождение пар не проверить;
- **ставка в год или в месяц** — Q13: у неустойки всё по дням, вторая база
  начисления запрещена;
- **обязательная ступень с порогом 0** — правило кредитора может начинать позже;
  ступень с бо́льшим порогом это и есть форма, а не пропуск;
- **порог строго в днях как float/Decimal** — порог это целое число дней.

❓ **02-Т3** — **Потолок: форма**: правка 1 — «без потолка» явная форма, не
`None`; формы: «без потолка», «сумма», «доля просроченной суммы».

➡️ Рекомендация (принята): **`PenaltyCap(kind: str, value: Decimal | None)`** с
константами `CAP_NONE = "без потолка"`, `CAP_SUM = "сумма"`,
`CAP_SHARE = "доля просроченной суммы"`. Поле `cap` у `PenaltyRule`
обязательно, включая `CAP_NONE` (правка 1). Валидация: у `CAP_NONE` —
`value is None`; у `CAP_SUM` и `CAP_SHARE` — `value > 0`. Различимость
«без потолка» и «правила нет» запирается тестом (приёмка 02).

*Отклонено:*
- **`cap=None` как «без потолка»** — правка 1: два смысла у одного маркера
  против `unknown-is-not-zero`;
- **отсутствие `value` как «без потолка»** — та же ловушка другим полем;
- **три отдельных класса потолка** — одна форма с дискриминантом проще и
  проверяется одной валидацией.

❓ **02-Т4** — **Порядок распределения: форма**: R3-Q12 — перестановка частей без
повторов и со всеми частями.

➡️ Рекомендация (принята): **`AllocationRule(order: tuple[str, ...], effective:
date | None = None)`**; `order` — перестановка `PARTS`: все четыре части, без
повторов. Валидация: длина равна четырём, каждая часть из `PARTS`, повторов нет.

*Отклонено:*
- **неполный список («только нужные части»)** — R3-Q12 требует перестановку
  целиком: частичный порядок не определяет, куда идёт избыток;
- **`dict` «часть → приоритет»** — числа вместо порядка: лишняя степень свободы
  и второй формат одного и того же;
- **строка-перечисление** — парсинг вместо данных, а модель хранит данные.

❓ **02-Т5** — **Триггер-правило: форма и параметры штрафа**: условие — из
закрытого набора (R3-Q12); штраф, который породит срабатывание, должен быть
задан данными — иначе тикету 07 пришлось бы менять сущность тикета 02.

➡️ Рекомендация (принята): **`TriggerRule(condition: str, threshold_days: int |
None = None, threshold_amount: Decimal | None = None, charge_amount: Decimal |
None = None, charge_percent: Decimal | None = None, part: str, basis: str | None
= None, effective: date | None = None)`**. Константы условий:
`TRIGGER_OVERDUE = "срок прошёл, есть просроченная сумма"`,
`TRIGGER_FULL_UNPAID = "полная неуплата"`,
`TRIGGER_OVERDUE_DAYS = "просрочка не меньше порога"`,
`TRIGGER_OVERDUE_SUM = "сумма просрочки не меньше порога"`. Штраф задаётся
ровно одним из: `charge_amount > 0` (сумма) или `charge_percent > 0` (доля
просроченной суммы); `part` — часть, в которую идёт штраф (обязательна, без
умолчания); `basis` — свободная метка основания производного начисления.
Порог обязателен для пороговых условий и положителен. Исполнение правила
(срабатывание, дата, идемпотентность) — тикет 07.

*Отклонено:*
- **форма только с условием, без параметров штрафа** — правило неполно: штраф
  не с чем считать, а дописывать поля чужой сущности тикет 07 не может;
- **отдельная сущность «штраф»** — параметры начисления принадлежат правилу,
  которое его порождает;
- **`part` по умолчанию** — умолчаний правил в движке нет (R3-Q12, Constraints):
  часть штрафа обязана приходить из данных.

❓ **02-Т6** — **Тексты валидации**: тикет вводит их — по существу, называя
правило и что исправить (R3-Q12).

➡️ Рекомендация (принята): тексты по формам:

- «правило неустойки сделки {deal!r}: ступени должны возрастать, пороги — не
  отрицательные»;
- «правило неустойки сделки {deal!r}: ставка ступени не может быть
  отрицательной»;
- «правило неустойки сделки {deal!r}: потолок обязателен — включая „без
  потолка“ (правка 1)»;
- «правило неустойки сделки {deal!r}: у потолка „без потолка“ не бывает
  значения» / «…: у потолка „{kind}“ значение должно быть положительным»;
- «правило распределения сделки {deal!r}: порядок — перестановка четырёх частей
  без повторов: тело, проценты, неустойка, издержки»;
- «правило триггера сделки {deal!r}: условие {condition!r} не входит в набор
  условий: …»;
- «правило триггера сделки {deal!r}: штраф задаётся ровно одним из — сумма или
  доля просроченной суммы»;
- «правило триггера сделки {deal!r}: у условия „…“ порог должен быть задан и
  быть положительным»;
- «правило {правило} сделки {deal!r}: версия без даты действия допустима,
  только если она одна»;
- «правило {правило} сделки {deal!r}: даты действий должны возрастать».

*Отклонено:*
- **один общий текст «некорректное правило»** — R3-Q12: текст называет причину;
- **исправлять данные движком** — правится не число, а данные зоны.

Фронтюр после раунда 1: края форм (даты на границе действия, пороги в точности
N дней) и структура тестов — зависят от форм выше, выносятся в раунд 2.

### Раунд 2 — края форм и структура тестов

Фронтюр: вопросы, разблокированные формами раунда 1 — краевые случаи дат и
порогов внутри форм и структура синтетических тестов.

❓ **02-Т7** — **Края форм**: что делать с датой действия ровно на границе, с
порогом ступени в точности N дней, с правилом из будущего и с пустым списком
правил.

➡️ Рекомендация (принята):

- **дата действия ровно на дате расчёта** — версия действует с этой даты
  включительно: правило с `effective = 2026-03-01` обслуживает и 2026-03-01;
- **порог ступени в точности N дней** — ступень действует включительно
  (возраст ровно N — берётся ступень «от N дней»);
- **правило с `effective` в будущем** — легально: до своей даты оно не
  действует, история считается прежней версией (или без правила);
- **пустой список правил** (`()`) — «правило не задано»: `rule_at` возвращает
  `None`, и это «не оценено»/пробел, а не ноль (R3-Q12);
- **две версии с одной датой** — ошибка валидации (даты строго возрастают).

*Отклонено:*
- **версия действует «после даты» (исключительно)** — расходится с «дата
  смены — дата передачи» (R4-Q25): правило меняется в тот же день, что и
  держатель;
- **`None` вместо пустого кортежа для «нет правил»** — два обозначения пустоты;
  пустой кортеж уже «правила нет», а `None` возвращается как результат выбора;
- **запрет правил из будущего** — зона пишет правила заранее, это её данные.

❓ **02-Т8** — **Структура синтетических тестов**: что запирает форму каждой
правила, версии и различимость «без потолка» / «правила нет».

➡️ Рекомендация (принята): `tests/test_settlements.py`. Группы:

1. **Валидация форм**: по одному положительному случаю на форму (шкала с
   порогом 0 и без, потолок во всех трёх видах, порядок-перестановка, триггер с
   суммой и с долей штрафа) и по одному отрицательному на текст (все тексты
   02-Т6: убывающие ступени, отрицательная ставка, отсутствующий потолок,
   значение у `CAP_NONE`, неполный порядок, повтор части, чужое условие, оба
   параметра штрафа, ни одного, порог не задан/неположителен).
2. **Версии и `rule_at`**: версия с датой обслуживает только свои даты (границы
   — день до, сам день, день после); две версии — история считается по своей;
   версия без даты — вся линия; версия без даты при второй версии — ошибка;
   две даты одинаковые — ошибка; правило из будущего не действует раньше срока.
3. **«Правила нет» против «без потолка»**: пустой список → `rule_at` → `None`;
   `PenaltyCap(CAP_NONE)` — известное «не ограничено»: значения нет и валидация
   его не требует; `CAP_SUM`/`CAP_SHARE` без значения — валидация падает. Здесь
   проверяется форма, а не обрезание: обрезание потолком — механика неустойки
   (тикет 06), и готовые факт-начисления тикета 01 оно не переписывает
   (01-Т4: тихая нормализация запрещена).
4. **Грани сверх приёмки**: ступень «от 0 дней» покрывает первый день просрочки
   (возраст 1); пороги в точности N дней (возраст ровно N — включительно).

*Отклонено:*
- **тесты срабатывания триггеров** — исполнение, отдано тикету 07;
- **тесты начисления неустойки по шкале** — расчёт, отдан тикету 06 (здесь
  только форма: «обрезание потолком» проверяется факт-начислениями, без формулы);
- **тест `allocate_payment`** — механика распределения, отдана тикету 03.

Фронтюр после раунда 2 пуст: форма, версии, валидация и их тесты определены;
исполнение правил — тикеты 06 и 07.
