# Решение: правила зоны и их формы

- Дата: 2026-10-02
- Статус: принято

## Контекст

Ставки, пороги, потолки и порядки распределения приходят снаружи: движок их
не вшивает и умолчаний не держит — личных и юрисдикционных чисел в нём быть
не должно. При этом движок обязан сам отвечать «сколько набежит, если тянуть
до даты» и сходиться с прокатом: правило начисления не должно жить вне
движка — тот самый обходной путь «пени держу в уме», который закрывает заявка
(план `penalties-and-charges`, R1-Q3).

## Варианты

1. **Правила приходят снаружи, считает движок (Q3).** Шкала неустойки, пороги,
   потолки и условия триггеров — данные модели зоны (как ставка и правило
   графика); движок применяет их к фактам книги. Иначе «сколько набежит» и
   «долг на дату» не сойдутся с прокатом.
   *Отклонено:* зона приносит готовые суммы начислений — будущие не записать
   заранее, «сколько набежит» движок не ответит; правила по умолчанию в
   движке — вшитые числа запрещены; триггер как вхождение графика — смешивает
   «не уплатил» с плановым платежом.
2. **Закрытый объявленный набор форм правил с валидацией (Q12).** Шкала
   неустойки — ступени «от N дней — дневная ставка»; потолок — сумма или доля
   просроченной суммы; порядок распределения — перестановка объявленного
   набора частей; условие триггера — из закрытого набора. У формы свои поля и
   своя проверка; валидация падает текстом по существу — называет сделку или
   правило и что исправить.
   *Отклонено:* свободная структура правила — движок не сможет ни проверить,
   ни исполнить произвольное правило, механика уедет в зону; правило-функция
   от зоны — зависимости в «нуле зависимостей» и личное правило вне сверки;
   правила по умолчанию — `None` честнее умолчания.
3. **Одно правило распределения платежа на сделку — правило кредитора
   (Q9).** Его вносит зона; сверка идёт по частям с тем же правилом. Кредитор
   распределил иначе — это расхождение, и закрывается оно записью факта
   (разбивкой движения) либо правкой правила зоны, а не правкой числа.
   *Отклонено:* два правила (моё и кредитора) и два расчёта — два ответа на
   один вопрос; правило по умолчанию в движке — молча порождает расхождение у
   любого кредитора с иным порядком; молчаливое распределение без разбивки —
   сверка по частям не сойдётся молча.
4. **Правила версионируются по дате действия (Q25).** Прошлое считается
   правилом своей эпохи — сверка на прошлые даты сходится; правило без даты
   действует весь период и допустимо, только если версия одна. Дата смены при
   цессии — дата передачи; правило меняет содержимое, части этого не касаются.
   *Отклонено:* одно правило на весь период — после смены кредитора история не
   сойдётся с выпиской навсегда; пересчёт истории новым правилом —
   переписывание прошлого; хранение посчитанного начисленного — второй носитель
   производной.
5. **Срабатывание триггера — по фактам книги, начисление производно
   (Q11, Q29).** Дата срабатывания — когда условие стало истинным («дата
   срока» — частный случай условия «срок прошёл», у порогового — дата
   достижения порога). Повторный прогон идемпотентен по построению:
   хранимых сгенерированных начислений нет, платёж задним числом пересчитывает
   — просрочка снимается, начисление откатывается само, сторно не нужно.
   *Отклонено:* движок сам пишет сгенерированные начисления в книгу — движок
   без состояния, книга принадлежит зоне, и повторный прогон насчитал бы
   дважды; сторно отдельными записями — второй носитель начисленного;
   идемпотентность счётчиком применений — состояние вне книги; «всегда дата
   срока» — пороговое условие лгало бы; дата расчёта — движок не спрашивает
   «сегодня».
6. **Триггер-правило опознаётся уидом; ключ случая — «уид правила, дата
   срабатывания» (Q35).** `basis` остаётся свободной меткой «что случилось» и
   опознания не даёт; запись-факт, вытесняющая случай, несёт ссылку на правило
   (`Charge.trigger`), и её дата — дата срабатывания; два факта с одним ключом
   — дубль, валидация падает; правка `basis` связь не ломает.
   *Отклонено:* ключ (basis, дата) — свободный текст: два правила одного
   основания в один день слились бы, правка основания рвала бы связь;
   опознание по составу правила — правка текста ломает опознание; uid
   опциональным — опознание обязано быть надёжным всегда.

## Решение

**Правила зоны — данные закрытых форм с валидацией; исполнение — движок.**
Формы: шкала неустойки, потолок, порядок распределения, условия триггеров —
каждая с датой действия (версии по эпохам), у триггера — uid и параметры
штрафа. Движок считает производно и идемпотентно, применяя правило своей
эпохи; порядок распределения — один на сделку, правило кредитора. Нет правила
— `None` или пробел, прогноз неполный, не ноль.

## Последствия

- Расширение набора форм — новая форма кодом движка, а не произвольная
  структура зоны.
- Правила нового кредитора при цессии — версия с датой передачи: история не
  пересчитывается, сверка на прошлые даты сходится.
- Идемпотентность триггеров — свойство, а не обещание: повторный прогон даёт
  те же случаи, хранимых сгенерированных начислений нет.
- Неизвестное правило — пробел с именем сделки в прогнозе, а не тихий ноль
  (`unknown-is-not-zero.md`).
