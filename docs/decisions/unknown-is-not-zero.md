# Решение: неизвестное значение — не ноль

- Дата: 2026-09-11
- Статус: принято

## Контекст

В исходных данных много `?`: прожиточный минимум, остаток по кредиту, сумма
взыскания. Решения при этом принимать нужно — ждать полных данных нельзя.

Первая версия ядра считала неполные данные молча: если прожиточный минимум не
задан, он просто не влиял на результат. Это дало **ложное успокоение** — «дыры
нет» звучало как «всё хорошо», хотя значило «мы не знаем, хватит ли на еду».
Тот же класс ошибки нашёлся в собственной реализации: если в окне сценария нет
будущего прихода и не задан горизонт, оценка возвращала 0 («нехватки нет») вместо
«оценить нечем».

## Варианты

1. **Подставлять ноль или оценку по умолчанию.** Просто, но выдаёт выдуманную
   уверенность: `?` превращается в незаметный ноль.
2. **Отказываться считать целиком, пока есть `?`.** Честно, но выбрасывает то,
   что посчитать можно: дыру, остатки, срок по известным долгам.
3. **Считать что можно, неизвестное возвращать как `None`.** Результат частичный,
   но каждая его часть помечена: «посчитано» или «не оценено».

## Решение

Вариант 3. Контракт:

- `Result.floor_gap = None` — прожиточный минимум неизвестен **или** не нашлось ни
  одного шага с известным приходом впереди.
- Долг с неизвестным остатком в прокат не входит и перечисляется потребителем как
  пробел.
- Не смоделированный поток называется пробелом, а не нулём.
- `Plan.stalled` вместо ложного срока, когда платёж меньше процентов.

## Последствия

- Ядро не имеет права «достроить» недостающее значение — только вернуть `None`.
- Потребитель обязан показать пробелы явно; отчёт без списка пробелов считается
  неполным.
- Цена: отчёты длиннее и содержат список пробелов. Это осознанно: пропущенный
  пробел дороже лишней строки.
