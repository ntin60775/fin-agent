# Решение: ядро — библиотека, а не база данных

- Дата: 2026-09-11
- Статус: принято

## Контекст

В финансовой зоне дыра на дату была посчитана неверно: расхождение вылезло на
сверке. Причина не в арифметике: правило «платёж идёт с конкретной карты, на
которой уже лежат деньги, значит переводим разницу» жило **только в прозе**. Каждый
расчёт заново выводил его из текста и один раз вывел неверно.

Вопрос: нужна ли вычислительная система и в какой форме, чтобы такие ошибки не
повторялись.

## Варианты

1. **Готовый DSL или фреймворк.** Рассматривались rule-движки (`pyke`, `drools`),
   формульные движки (`formulas`, `pycel`), plain-text-бухгалтерия (`beancount`,
   `hledger`), решатели ограничений (`z3`, `ortools`). Отпало: ни одно не решает
   задачу «какой счёт финансирует платёж и где касса уходит в минус».
2. **Своя база данных со своим файлом данных** (как в прежней наработке: SQLite,
   intake-пайплайны, privacy-слой — 5 606 строк, из них расчётное ядро 823).
   Отпало: цифры уже живут в markdown, второй носитель даёт расхождение — ровно
   тот класс ошибок, который лечим.
3. **Ядро парсит markdown.** Отпало: markdown не машиночитаем, парсер хрупок.
4. **Библиотека без состояния.** Цифры → сценарий на стороне потребителя → ядро.
   Ядро не хранит состояние и не читает markdown: считает то, что передали.

## Решение

Вариант 4. `finance_core` — библиотека на стандартной библиотеке Python
(деньги — `Decimal`, ноль внешних зависимостей). Источник правды по цифрам — на
стороне потребителя; ядро — источник правды по арифметике.

## Последствия

- Правило счёта, найденное по ходу, обязано переехать в код и под тест; прецедент
  с двойным учётом заперт тестом `test_payment_hits_its_funding_account`.
- Ядро не может «посмотреть в файл» — значит, сценарий собирается вызывающим
  кодом, и расхождение цифр ловится на его стороне.
- Цена: библиотеку нельзя использовать как готовый продукт — нужен потребитель,
  который её наполнит.
